PRD: Automated Lecture Transcription, Notes & Study-Aid
System
Version: 2.0 Author: Shital P. Status: Draft — Planning Phase Domain: CS/Engineering
classroom lectures (Kannada/English/Kannada-accented-English), hosted web platform
1. Problem Statement
Lecturers teach in class while students take notes in real time. In doing so, students often
miss points, mishear things, or fail to note anything at all for stretches of the lecture —
resulting in incomplete or missing notes that only get discovered as a gap the night
before an exam. There is no free, hosted platform that turns a lecture directly into
accurate, structured study material available to the whole class immediately after the
lecture — and no existing tool gives lecturers feedback on their own delivery (pacing,
repeated words, etc.) to improve teaching quality.
Classroom environment (confirmed with faculty): These are high-quality classroom
setups — not noisy general classrooms. Low echo, low background noise, and audio is
captured via a mic on the lecturer directly. This meaningfully de-risks the transcription
problem compared to a generic noisy-classroom assumption; noise-cleanup is still
included as a safety net, but is not the primary technical risk it would be with
ambient/laptop-mic recording.
2. Goal
Build a fully free, hosted/online platform with two distinct dashboards:
1. Faculty dashboard — upload lecture audio → get accurate transcript → auto-
generated notes, summary, flashcards, quiz, and glossary → review and broadcast to
enrolled students. Separately, faculty get a lecture analytics dashboard (pacing,
filler/repeated-word frequency, keyword usage) to self-improve teaching delivery.
2. Student dashboard — simple login (no email needed) → see broadcast
notes/summary/flashcards/quiz/glossary for enrolled subjects as soon as faculty
publishes them, instead of scrambling before exams.
3. Non-Goals (for now)
PPT/board sync and OCR — deferred, revisit only if needed.
Real-time live captioning during class (post-lecture batch processing only, for
MVP).
Native mobile app (responsive web UI is sufficient).
Full-featured auth (email verification, password reset flows, SSO) — simple
credential-based login is enough for MVP.
Persistent/"remember me" login — nice-to-have, explicitly held off if it adds
complexity; MVP prioritizes basic login working reliably over session persistence.
Paid APIs or paid hosting tiers of any kind.

4. Users & Roles
4.1 Faculty
Uploads lecture audio for a specific subject/batch
Reviews the auto-generated notes/summary/flashcards/quiz/glossary before
publishing
Broadcasts the finished lecture package to the enrolled batch (students don't see it
until broadcast — this is a deliberate gate, not automatic publish-on-processing)
Views a per-lecture analytics dashboard: pacing, word frequency/filler words,
keyword usage
4.2 Student
Logs in with simple credentials (username/roll-no + password, no email required)
Sees only subjects/batches they're enrolled in
Once faculty broadcasts a lecture, sees: notes, transcript, flashcards, quiz, glossary,
and (Phase 2) knowledge graph across lectures
Takes quizzes, reviews flashcards (SRS in Phase 2) — progress tracked per student

6. Functional Requirements Detail
6.1 Transcription (Faculty side, backend)
Faculty uploads .mp3 / .wav / .m4a via dashboard, tagged with subject + batch


=== PAGE 5 ===
Since audio comes from a lecturer-worn mic in a controlled classroom, expected
input quality is good — light VAD/denoise as a safety net, not a heavy-lifting
requirement
Groq hosted whisper-large-v3 API for transcription (free tier, no local GPU
needed)
Chunk-level language handling so Kannada/English code-switching within a
lecture is handled per-segment rather than whole-file
Output: timestamped transcript (JSON + plain text), stored against that lecture
record
6.2 Faculty Review Step
Before broadcasting, faculty sees generated transcript + notes + flashcards + quiz +
glossary in a review UI
Can lightly edit transcript/notes if something is clearly wrong
Nothing reaches students until faculty explicitly clicks "Broadcast"
6.3 Notes & Summary Generation
Transcript chunked into topic segments (silence-gap + keyword-shift heuristic)
LLM (Groq free tier) generates: structured notes (headings/bullets/bold key terms,
proper math/CS notation) + a short lecture summary
Placeholders inserted for unclear sections rather than hallucinating content
6.4 Flashcards
LLM generates Q/A pairs per topic segment
Exportable to .apkg (Anki-compatible) via genanki
6.5 Quizzes
LLM generates MCQs (question + 4 options + correct answer + explanation)
Student-facing web UI: take quiz, self-check, score stored per student
6.6 Glossary
LLM extracts key terms + 1-line definitions per lecture
Phase 2: deduped and accumulated across lectures per subject, feeding back into
future transcription prompts
6.7 Lecture Analytics Dashboard (Faculty — Feature 2)
This is a first-class MVP feature, not a cherry. Computed directly from the transcript +
audio timing data, no extra model needed beyond what's already generated:
Pacing: words per minute overall, and variation across the lecture (e.g. segment-by-
segment WPM) — computed from transcript word count against timestamp spans
Word frequency / filler word tracking: frequency count of all words used, with
filler words ("so", "basically", "like", "actually", repeated crutch words) surfaced
distinctly so faculty can see overuse patterns


=== PAGE 6 ===
Keyword usage: how often key subject-relevant terms were mentioned (cross-
referenced against the lecture's own glossary output)
Presented as a simple per-lecture dashboard (bar chart of top repeated words,
WPM-over-time line, keyword frequency table) — no need for anything more
elaborate in MVP
Phase 2: trend view across multiple lectures so faculty can see if pacing/filler-word
patterns are improving over the semester
6.8 Simple Student Login
Username or roll-number + password, no email required
No password-reset flow needed for MVP (faculty/admin can reset manually if
needed at this scale)
Session persistence ("stay logged in") is Phase 2 — MVP is fine requiring login each
new browser session
6.9 Spaced Repetition (Phase 2)
SM-2 algorithm (ease factor, interval, next-review-date per card, per student)
Review UI: show card, self-rate recall, reschedule
6.10 Semantic Search (Phase 2)
Embed notes chunks ( sentence-transformers , free), store in pgvector or hosted
Chroma
Natural-language search across a subject's past lectures
6.11 Knowledge Graph (Phase 2)
LLM extracts concepts/relationships per lecture
NetworkX graph, Pyvis visualization, scoped per subject (cross-subject linking as a
stretch goal)

10. Development Phases
Phase 0 — Feasibility Validation
Record a real lecture sample using an actual lecturer mic setup in the described
classroom environment
Run through Groq's hosted whisper-large-v3 API
Confirm accuracy is high given the clean-audio assumption (this should be a much
shorter validation than originally planned, since noise/accent risk is lower than a
generic classroom)
Exit criteria: transcript is clean enough that faculty review is a light touch-up, not a
rewrite


=== PAGE 11 ===
Phase 1 — Hosted Skeleton + Auth + Enrollment Model
FastAPI backend on Railway/Render, Postgres on Supabase/Neon, React frontend
(two dashboard shells) on Netlify
Build faculty , students , subjects , batches , enrollments tables
Simple username/password login for both roles (no persistence yet — that's Phase
2+)
Exit criteria: a faculty account and a student account can both log in and see their
respective (empty) dashboards; enrollment correctly scopes what a student could
eventually see
Phase 2 — Upload → Transcription → Faculty Review
Audio upload flow tagged to subject/batch
Groq Whisper integration, transcript stored
Faculty review UI (view/edit transcript before generation runs, or after — decide
based on Phase 0 findings)
Exit criteria: faculty can upload a real lecture and get back a stored, readable
transcript in their dashboard
Phase 3 — Generation Pipeline + Broadcast (MVP core)
Topic chunking + LLM generation of notes/summary/flashcards/quiz/glossary
Faculty review of full generated package
Broadcast action — flips lecture status, makes it visible to enrolled students
Student dashboard: view notes/transcript/flashcards/quiz/glossary for broadcast
lectures only
Exit criteria: MVP complete — faculty uploads a real lecture, reviews the
generated package, broadcasts it, and an enrolled student logs in and sees/uses all
of it end to end
Phase 4 — Lecture Analytics Dashboard
Compute WPM (overall + per-segment) from transcript timestamps
Word frequency + filler-word detection (maintain a small filler-word list: "so",
"basically", "actually", "like", etc., plus raw top-frequency words)
Keyword frequency cross-referenced against that lecture's glossary
Simple faculty-only analytics view (charts/tables)
Exit criteria: faculty can open any of their own past lectures and see pacing + word-
frequency + keyword data
Phase 5 — Persistent Login (if it doesn't add undue complexity)
Session token / cookie-based "stay logged in" for students (and faculty)
Exit criteria: a student who logged in once doesn't need to re-enter credentials on
their next visit, without breaking the simple-login MVP flow
